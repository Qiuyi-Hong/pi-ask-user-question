# Research: GitHub Actions and npm publishing constraints

Checked-at: **2026-09-29 UTC**. Factual research for [Establish GitHub Actions and npm publishing constraints](https://github.com/Qiuyi-Hong/pi-ask-user-question/issues/3), child of [Chart an upstream-faithful TypeScript package with reviewed sync PRs](https://github.com/Qiuyi-Hong/pi-ask-user-question/issues/1).
Upstream: `juicesharp/rpiv-mono`, `packages/rpiv-ask-user-question`; downstream: `Qiuyi-Hong/pi-ask-user-question`.
Scope: supported mechanisms, authentication, execution boundaries, and registry constraints; **not** cadence, package name, version scheme, layout, or release policy.
Evidence labels: **Confirmed** = directly documented/API-observed; **Implication** = researcher interpretation/inference; **Unverified** = requires operational verification.

## Summary

An unrelated upstream push cannot natively trigger this repository's path-filtered workflow: downstream polling/manual dispatch is available, while prompt event delivery needs upstream-authorized cooperation and an authenticated downstream dispatch. [Workflow event scope](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#on), [external dispatch](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#repository_dispatch).
A downstream `GITHUB_TOKEN` can propose branches/PRs when permissions/settings/rules permit; current docs expressly allow token-generated `pull_request` **opened/synchronize/reopened** runs, but require a writer's workflow-run approval rather than silently suppressing all PR CI. [Current token behavior](https://docs.github.com/en/actions/concepts/security/github_token#when-github_token-triggers-workflow-runs).
A distinct public npm package requires publishing rights and immutable name/version identities; current authentication supports interactive 2FA, configured OIDC trusted publishing, and constrained granular tokens, with new stage-only defaults for trusted publishers and an announced January 2027 end to granular-token direct publishing. [Publishing](https://docs.npmjs.com/cli/v12/commands/npm-publish/), [trusted publishing](https://docs.npmjs.com/trusted-publishers/), [token restrictions](https://docs.npmjs.com/about-access-tokens/#direct-publishing-is-being-deprecated).

## Findings

### 1. External change detection and delivery

**Claim:** Downstream Actions can poll public upstream state or receive authorized dispatches, but do not subscribe natively to unrelated repository pushes. **Support:** direct evidence plus explicitly labeled interpretation. **Confidence:** high.

- **Confirmed:** GitHub documents `on: push` as pushes in the **workflow's repository**; `paths`/`paths-ignore` filter that event's changed paths. **Implication:** adding the upstream directory to downstream `push.paths` does not watch `juicesharp/rpiv-mono`; checking out that repository also does not create such a subscription. [Event scope](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#on), [path filters](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpushpull_requestpull_request_targetpathspaths-ignore).
- **Confirmed:** Live public GitHub API responses identify upstream as public (`private: false`) with default branch `main`, and return the requested package directory. This confirms public readability/path existence, not a chosen tracking ref or an upstream integration agreement. [Repository API](https://api.github.com/repos/juicesharp/rpiv-mono), [directory API](https://api.github.com/repos/juicesharp/rpiv-mono/contents/packages/rpiv-ask-user-question).
- **Confirmed:** `schedule` requires its workflow file on the default branch, runs only there, and uses its latest commit. The shortest supported interval is **five minutes**; UTC is the default, with optional IANA time zones now documented. [Schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
- **Confirmed:** Schedules can be delayed at high load, especially the beginning of an hour; sufficiently high load can **drop queued jobs**. Public-repository scheduled workflows auto-disable after **60 days without repository activity**. **Implication:** schedule polling is not a prompt-delivery SLA, and ongoing upstream activity does not establish downstream activity. [Schedule limitations](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
- **Confirmed:** `workflow_dispatch` must be declared and the file must exist on the default branch. The manual UI/CLI procedure requires downstream write access; a branch/tag can be selected. The event page additionally says that after a workflow has run at least once, API/CLI dispatch can target any branch/tag. Inputs allow **25 top-level properties**, with a **65,535-character** maximum payload. [Manual runs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow), [dispatch event](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch).
- **Confirmed:** `repository_dispatch` supports external activity but requires a workflow file on the default branch and uses the default-branch commit/ref. `event_type` is limited to **100 characters**; `client_payload` to **10 top-level properties** and **65,535 characters**. It is an API-created event, not an unauthenticated public webhook subscription. [Repository dispatch](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#repository_dispatch).
- **Confirmed:** Creating an upstream repository webhook requires ownership/admin access. An outsider cannot register an ordinary webhook merely because a repository is public. [Webhook creation authority](https://docs.github.com/en/webhooks/using-webhooks/creating-webhooks#creating-a-repository-webhook).
- **Confirmed:** The downstream REST `repository_dispatch` endpoint requires **Contents: write** for fine-grained tokens; `workflow_dispatch` requires **Actions: write** and a branch/tag `ref`. Both support appropriately authorized GitHub App tokens/fine-grained PATs. [Repository API](https://docs.github.com/en/rest/repos/repos#create-a-repository-dispatch-event), [workflow API](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event).
- **Implication:** Prompt delivery can use an upstream-maintainer-managed workflow/integration that dispatches downstream, or an upstream-authorized webhook to an external receiver that authenticates to dispatch downstream. The receiver requires signature/input validation and protected dispatch credentials; upstream's own `GITHUB_TOKEN` does not acquire downstream write authority. This is a mechanism, not provisioning advice or a guaranteed delivery time. [Webhook authority](https://docs.github.com/en/webhooks/using-webhooks/creating-webhooks#creating-a-repository-webhook), [token scope](https://docs.github.com/en/actions/concepts/security/github_token#about-the-github_token).
- **Confirmed:** Public REST ref/tree/content endpoints expose ref SHAs, tree/blob identities, and path contents; contents can be selected at a `ref`. Recursive trees can truncate at **100,000 entries / 7 MB**; truncated results require non-recursive subtree traversal. [References](https://docs.github.com/en/rest/git/refs#get-a-reference), [trees](https://docs.github.com/en/rest/git/trees#get-a-tree), [contents](https://docs.github.com/en/rest/repos/contents#get-repository-content).
- **Implication:** Polling a ref plus the selected package subtree/path signal is feasible without executing upstream code. A whole-monorepo ref change need not change the package subtree, while a package-only signal can miss relevant shared files/dependencies. Preserve the observed upstream commit/tree identities for review; the definition of the complete snapshot remains outside this ticket.

### 2. Read quotas, proposal permissions, and repository rules

**Claim:** Public reading and downstream mutation are different authorization problems; token scopes do not override repository rules or establish independent review. **Support:** direct evidence and interpretation. **Confidence:** high.

| Operation | Confirmed constraint / primary source |
| --- | --- |
| Unauthenticated public REST reads | **60 requests/hour per originating IP**, not per workflow. [REST limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#primary-rate-limit-for-unauthenticated-users) |
| PAT/OAuth/GitHub App user-token REST requests | Normally **5,000/hour per user**; Enterprise Cloud exceptions exist. [Authenticated limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#primary-rate-limit-for-authenticated-users) |
| GitHub App installation REST requests | Minimum **5,000/hour**, scaling for qualifying installations up to **12,500**; Enterprise Cloud installations **15,000/hour**. [Installation limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#primary-rate-limit-for-github-app-installations) |
| Actions `GITHUB_TOKEN` REST requests | **1,000/hour per repository**; **15,000/hour** for requests to Enterprise Cloud resources. [Actions limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#primary-rate-limit-for-github_token-in-github-actions) |
| Downstream branch create/update | Ref APIs require **Contents: write**; the docs also list Contents + **Workflows: write** for applicable workflow-changing operations with fine-grained credentials. Updating a ref defaults to non-force/fast-forward behavior. [Create ref](https://docs.github.com/en/rest/git/refs#create-a-reference), [update ref](https://docs.github.com/en/rest/git/refs#update-a-reference) |
| Downstream PR create/update | REST APIs require **Pull requests: write**; public PR opening/updating requires write access to its source/head branch. [Create PR](https://docs.github.com/en/rest/pulls/pulls#create-a-pull-request), [update PR](https://docs.github.com/en/rest/pulls/pulls#update-a-pull-request) |

- **Confirmed:** Save an endpoint's `ETag`, then send `If-None-Match` on subsequent GETs. Unchanged responses return **304**. A 304 does not consume **primary** quota only when the request is correctly authenticated with an `Authorization` header; do not claim unauthenticated 304s are quota-free. `Last-Modified`/`If-Modified-Since` is another supported conditional mechanism. [Conditional requests](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#use-conditional-requests).
- **Confirmed:** GitHub recommends stable, specific requests when polling, respecting `x-poll-interval` if present. Secondary limits still apply; use response `x-ratelimit-*` headers and `retry-after`/documented backoff for 403/429 errors. [Polling practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#avoid-polling), [secondary limits/backoff](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#about-secondary-rate-limits).
- **Confirmed:** `GITHUB_TOKEN` is a per-job GitHub App installation token whose permissions are limited to the repository containing the workflow. Public upstream ref/tree/content reads need no upstream permission; public readability is **not** upstream write authorization, nor does it mean a downstream token is installed upstream. [Token scope](https://docs.github.com/en/actions/concepts/security/github_token#about-the-github_token), [public ref reads](https://docs.github.com/en/rest/git/refs#get-a-reference).
- **Confirmed:** Workflow/job `permissions` can explicitly grant `contents: write` and `pull-requests: write`; setting any permissions makes unspecified ones `none`. Settings/policies constrain effective access. The separate repository setting **Allow GitHub Actions to create and approve pull requests** controls whether `GITHUB_TOKEN` may do those operations. [Permission syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions), [repository Actions settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository#preventing-github-actions-from-creating-or-approving-pull-requests).
- **Confirmed:** Rulesets can restrict branch creation/update/deletion, force pushes, signing, required PRs/reviews, and required checks. Write scope is not a bypass grant. Merely requiring a PR does **not** necessarily require its approval; the additional review rules matter. [Available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).
- **Implication:** Proposal automation can copy an upstream snapshot as data and create/update a downstream source branch and PR, without editing the upstream bytes or merging it. Grant mutation rights only to trusted proposal logic. The setting that permits both creation and approval is not itself a human-review guarantee; human review/merge must remain a separate operation and applicable repository control.

### 3. Exact current `GITHUB_TOKEN` event behavior and CI deadlocks

**Claim:** The old blanket assertion that token-created PRs cannot trigger CI is no longer correct in current GitHub.com documentation. **Support:** direct evidence. **Confidence:** high for documented behavior; actual downstream operation untested.

| Event caused using downstream `GITHUB_TOKEN` | Current documented behavior |
| --- | --- |
| `push` | Does **not** create another workflow run, including pushes to a PR branch when considering the `push` event itself. |
| `pull_request` `opened`, `synchronize`, `reopened` | Creates matching workflow runs in an **approval-required** state. A user with repository **write** access selects **Approve workflows to run** in the PR merge-box banner. |
| Other `pull_request` activity, e.g. `labeled`, `edited`, `closed` | Does **not** create workflow runs through this exception. |
| `workflow_dispatch`, `repository_dispatch` | Explicit exceptions that create runs, subject to the workflow/event configuration and authorization requirements. |

Sources for the entire matrix: [GITHUB_TOKEN event behavior](https://docs.github.com/en/actions/concepts/security/github_token#when-github_token-triggers-workflow-runs), independently repeated in [Triggering a workflow](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow).

- **Confirmed:** To have automation-created/updated PR workflows execute without that token-specific approval prompt, GitHub documents a **separate GitHub App installation token or PAT** instead of `GITHUB_TOKEN`. This changes event generation, not the trustworthiness of the proposed content or other repository safeguards. [Alternatives](https://docs.github.com/en/actions/concepts/security/github_token#when-github_token-triggers-workflow-runs).
- **Confirmed:** Ordinary GitHub App installation tokens expire after **one hour** and cannot exceed their installation's repositories/permissions. The built-in job token expires at job end or its effective maximum lifetime; current docs give **six hours** maximum on GitHub-hosted runners and up to **24 hours** of refresh on self-hosted runners. [App token bounds](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app), [job token bounds](https://docs.github.com/en/actions/concepts/security/github_token#about-the-github_token).
- **Confirmed:** Branch/path/commit-message filtering can leave a required workflow's checks **Pending**, blocking merge. `pull_request` workflows also do not run when the PR has a merge conflict. [Skipped checks](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#using-filters-to-target-specific-paths-for-pull-request-or-push-events), [PR conflicts](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request).
- **Implication:** A push-only required check can wait forever after a `GITHUB_TOKEN` push; a token-generated PR run waits for workflow approval. Neither problem is solved by declaring the bot's snapshot trusted. A matching approved PR run, explicit dispatch, or alternative event-generating identity is a supported mechanism; which becomes mandatory is not decided here.
- **Confirmed:** PR workflows normally use the synthetic merge commit, not necessarily the candidate head SHA. `actions/checkout` supports an explicit branch/tag/SHA and documents `github.event.pull_request.head.sha` for head-commit testing. [PR event SHA](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request), [checkout head](https://github.com/actions/checkout#checkout-pull-request-head-commit-instead-of-merge-commit).
- **Implication — explicit safe validation option:** Dispatch a trusted validator definition from the downstream **default branch**, with PR number and immutable candidate SHA as inputs. Validate the input format and PR/repository/head association with read-only API calls, explicitly checkout that SHA with `persist-credentials: false`, and assert/log the actual checked-out SHA before running candidate tests in the restricted job described below. Do not select the candidate branch as the validator's workflow `ref`, or interpolate untrusted input into shell source. [Dispatch inputs/ref](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event), [checkout SHA/credentials](https://github.com/actions/checkout#usage), [script injection guidance](https://docs.github.com/en/actions/reference/security/secure-use#good-practices-for-mitigating-script-injection-attacks).
- **Implication:** Dispatching trusted workflow code with a candidate-SHA input does not automatically attach its Actions check to that candidate: `GITHUB_SHA` follows the dispatched ref. Record the tested SHA and recheck PR-head freshness before review/merge. Any later required-check/status association needs a trusted reporting mechanism and proof that the result matches that exact SHA; it must not grant validation code status-write access. [Dispatch SHA semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch), [required checks/status sources](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-status-checks-to-pass-before-merging).

### 4. Safe execution of upstream-controlled content

**Claim:** Byte-for-byte copying does not make install scripts, builds, tests, dependencies, or workflow changes safe to run with proposal/release authority. **Support:** documented security facts plus engineering implications. **Confidence:** high.

- **Confirmed:** GitHub recommends least-privilege tokens and specifically warns against checking out untrusted code with `pull_request_target` or `workflow_run`, including repositories outside your control. These privileged contexts can expose write tokens, secrets, and default-branch caches. `workflow_run` may gain secrets/write tokens even when its predecessor had none. [Secure use](https://docs.github.com/en/actions/reference/security/secure-use#mitigating-the-risks-of-untrusted-code-checkout), [workflow_run](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run).
- **Confirmed:** Fork `pull_request` workflows ordinarily receive read-only tokens and no repository secrets other than `GITHUB_TOKEN`. **Implication:** a bot branch created **inside downstream** is not such a fork: explicitly restrict its validation jobs instead of assuming fork defaults protect it. [Fork PR permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request).
- **Confirmed:** Checkout persists credentials by default; `persist-credentials: false` opts out. Current v6+ storage moved to a separate `$RUNNER_TEMP` file rather than direct `.git/config` storage. Current checkout also adds fork-checkout protection for privileged triggers; that is not a general sandbox for same-repository snapshots. [Checkout defaults/version changes](https://github.com/actions/checkout#usage).
- **Confirmed:** npm documents lifecycle execution for `ci`, `install`, `pack`, and `publish`, including prepare/prepack/publish hooks. `ignore-scripts` suppresses package scripts, but explicit `npm test`/`npm run` still execute their intended scripts. [Lifecycle order](https://docs.npmjs.com/cli/v12/using-npm/scripts/#life-cycle-operation-order), [ignore-scripts](https://docs.npmjs.com/cli/v12/using-npm/config/#ignore-scripts).
- **Confirmed:** npm v12 changed dependency install-time security defaults: lifecycle scripts/implicit node-gyp builds need approval, and Git/remote-URL dependencies are opt-in. **Implication:** this does not sandbox root project hooks, explicit build/test scripts, or an upstream-controlled allowlist/configuration; do not use an old “all dependency scripts always run” assertion or a new “npm v12 makes installs safe” assertion. [v12 shipped defaults](https://github.blog/changelog/2026-07-08-npm-install-time-security-and-gat-bypass2fa-deprecation/), [script execution](https://docs.npmjs.com/cli/v12/using-npm/scripts/).
- **Implication:** Validate candidate install/lifecycle/build/test behavior on a fresh isolated GitHub-hosted runner with explicit **read-only repository token**, **no npm publish token**, **no App/PAT write token**, **no release/cloud secrets**, **no release environment**, and **no `id-token: write`**. Credentials that may mint publishing authority are credentials too. If private dependencies need authentication, that is a separately reviewed exposure, not permission to lend release credentials to candidate code. [Least privilege](https://docs.github.com/en/actions/reference/security/secure-use#use-secrets), [OIDC authority](https://docs.npmjs.com/trusted-publishers/#github-actions-configuration).
- **Implication:** Keep trusted proposal mutation separate from candidate execution; no executing checked-out upstream scripts, local actions, or changed workflow definitions in the writer. New/modified `.github/workflows` content is executable authority and must be reviewed as such, not adopted merely to test the snapshot. Treat fetched paths, symlinks, archives, branch names, PR text, and dispatch fields as untrusted input. [Untrusted checkout/injection risks](https://docs.github.com/en/actions/reference/security/secure-use).
- **Confirmed:** GitHub warns that actions/jobs can compromise other jobs through shared environments/directories/runner resources; it cautions about artifacts from `workflow_run` and the risks of self-hosted runners for public repositories. **Implication:** splitting steps or merely withholding a token from a later command is not sufficient. Use separate isolated jobs/runners with per-job permissions and short-lived credentials; do not execute untrusted artifacts or restore attacker-influenced executable caches in a privileged job. [Job interaction](https://docs.github.com/en/actions/reference/security/secure-use#using-third-party-actions), [runner/artifact risks](https://docs.github.com/en/actions/reference/security/secure-use).
- **Implication:** Crossing a validation boundary requires independently verifying structured results, identity, run provenance, and exact SHA, not executing uploaded scripts or treating success/artifact existence as authorization. A human workflow-run approval allows execution; PR review/merge approval and npm publication approval are different decisions. None is replaced by the others.

### 5. npm identities, ownership, visibility, and valid versions

**Claim:** Downstream publication needs its own authorized identity and a new immutable version for changed content; dist-tags do not create a replacement tarball identity. **Support:** direct evidence plus interpretation. **Confidence:** high.

- **Confirmed:** A user/org gets an npm scope matching its name; separate scopes permit the same package-name suffix without conflict. Package maintainers can modify metadata/publish versions; a public source repository does not transfer another npm package/scope's ownership. **Implication:** distinct downstream publication needs an available unscoped name or rights in a downstream-owned/authorized scope, not use of upstream ownership by copying its manifest. [Scopes](https://docs.npmjs.com/about-scopes/), [maintainers](https://docs.npmjs.com/cli/v12/commands/npm-owner/).
- **Confirmed:** New names are at most **214 characters including scope**, have no uppercase letters or non-URL-safe characters, and unscoped names may not start with dot/underscore. Publication requires `name` and `version`; `private: true` makes npm refuse publication. [Manifest constraints](https://docs.npmjs.com/cli/v12/configuring-npm/package-json/#name), [private guard](https://docs.npmjs.com/cli/v12/configuring-npm/package-json/#private).
- **Confirmed:** Public scoped publishing is supported with explicit **`--access public`**. General scope/how-to docs say scoped packages default private, but current **v12** publish docs say **new packages default public**; explicit access avoids relying on the contradictory default descriptions. Unscoped packages cannot be restricted. [Scoped public publishing](https://docs.npmjs.com/creating-and-publishing-scoped-public-packages/#publishing-scoped-public-packages), [v12 access](https://docs.npmjs.com/cli/v12/commands/npm-publish/#access).
- **Confirmed:** Once published, **`name@version` can never be used again**, even after unpublish; publication fails if that combination exists. Unpublish is constrained and is not a way to replace a version's contents. [Publish identity](https://docs.npmjs.com/cli/v12/commands/npm-publish/#description), [unpublish policy](https://docs.npmjs.com/policies/unpublish/).
- **Confirmed:** A version must be parseable by npm's `node-semver`. SemVer core is `X.Y.Z` with nonnegative integers and no leading zeros; prerelease identifiers are nonempty ASCII alphanumeric/hyphen strings, with no leading zeros in numeric identifiers. Build identifiers use the same character set and do not affect precedence. No downstream version scheme is selected here. [npm version requirement](https://docs.npmjs.com/cli/v12/configuring-npm/package-json/#version), [SemVer 2.0.0 §§2,9–11](https://semver.org/spec/v2.0.0.html#semantic-versioning-specification-semver).
- **Confirmed:** Dist-tags are labels pointing to published versions; `latest` is the normal publish tag, and tag names share the version namespace. **Implication:** moving a tag changes selection, not `name@version`/tarball identity, and cannot repair immutable contents. [Dist-tags](https://docs.npmjs.com/adding-dist-tags-to-packages/).

### 6. Current npm 2FA, manual approval, and granular tokens

**Claim:** npm authentication requirements and maintainers' review policy are separate; current supported automation is not classic-token publishing. **Support:** direct evidence. **Confidence:** high, with documentation discrepancies recorded below.

- **Confirmed:** Current package-security docs require **2FA or a granular token with bypass-2FA** for package creation/publication; package-settings modification also requires 2FA. The default new-package setting is **Require two-factor authentication or a granular access token with bypass 2fa enabled**; interactive `npm publish` prompts for a second factor. [Package 2FA](https://docs.npmjs.com/requiring-2fa-for-package-publishing-and-settings-modification/).
- **Confirmed:** **Require two-factor authentication and disallow tokens** blocks granular-token publishing regardless of bypass setting, but does **not** block configured OIDC trusted publishers. Thus “disallow tokens requires every OIDC publish to be interactive” is incorrect. [Package settings](https://docs.npmjs.com/requiring-2fa-for-package-publishing-and-settings-modification/), [OIDC exception](https://docs.npmjs.com/trusted-publishers/#recommended-restrict-token-access-when-using-trusted-publishers).
- **Confirmed:** `npm login` produces a **two-hour session**; publication within it still enforces 2FA. All npm **classic tokens were permanently revoked on December 9, 2025** and cannot authenticate, be recreated, or recovered. These are npm tokens, not GitHub PATs. [Completed migration announcement](https://github.blog/changelog/2025-12-09-npm-classic-tokens-revoked-session-based-auth-and-cli-token-management-now-available/).
- **Confirmed:** Granular tokens can restrict packages/scopes, org permissions, CIDR ranges, read/write access, expiry, and bypass-2FA; bypass is off by default. Selected package/scope permissions do not exceed the user's rights, and revocation of user access revokes corresponding token access. Org-management permission alone does not grant package publishing. [Granular scope](https://docs.npmjs.com/about-access-tokens/#about-granular-access-tokens).
- **Confirmed:** The docs allow up to **1,000 granular tokens/account**, **50 selected packages/scopes combined** and **50 orgs/token**; creation also exposes an all-packages option. Treat that as broader scope, not a safer shortcut. Website custom expiry must be at least **one day** ahead. [Limits](https://docs.npmjs.com/about-access-tokens/#about-granular-access-tokens), [selection/expiry](https://docs.npmjs.com/creating-and-viewing-access-tokens/#creating-granular-access-tokens-on-the-website).

| npm credential | Current lifetime / publishing scope |
| --- | --- |
| Login session | **2 hours**; user's authorization plus interactive publishing 2FA. [Completed change](https://github.blog/changelog/2025-12-09-npm-classic-tokens-revoked-session-based-auth-and-cli-token-management-now-available/) |
| Granular read-write, including stage-only | **7-day default; 90-day maximum**, scoped package/permission authorization. [First-party token API spec, `expires`](https://github.com/npm/api-documentation/blob/main/api/registry.npmjs.com/token.yaml) |
| Granular read-only | **30-day default; unlimited maximum** in the current API spec; cannot publish. Do not apply the write-token 90-day cap to read-only tokens. [Token API spec](https://github.com/npm/api-documentation/blob/main/api/registry.npmjs.com/token.yaml) |
| OIDC-exchanged registry token | Package-scoped; API overview says **typically one hour**, not a guaranteed invariant. Exchange response supplies `created`/`expires`; request audience must be **`npm:registry.npmjs.org`**. [API overview](https://github.com/npm/api-documentation/blob/main/api/base.yaml), [OIDC exchange spec](https://github.com/npm/api-documentation/blob/main/api/registry.npmjs.com/oidc.yaml) |

- **Confirmed:** Since **August 2026**, bypass-2FA granular tokens cannot perform account-identity/governance actions such as token management, package maintainer/access/trust changes, org/team governance, or unpublish; those need an interactive second-factor challenge. [Current restrictions](https://docs.npmjs.com/about-access-tokens/#account-identity-actions-require-an-interactive-2fa-challenge), [API restrictions](https://github.com/npm/api-documentation/blob/main/api/base.yaml).
- **Confirmed:** Direct-capable bypass-2FA tokens can still directly publish **as checked**, subject to package settings, but docs announce removal of granular-token direct publication in **January 2027**. This is an announced future restriction, not a claim that direct publishing already fails. [Deprecation](https://docs.npmjs.com/about-access-tokens/#direct-publishing-is-being-deprecated).
- **Confirmed:** Stage-only tokens cannot directly publish new versions (`E_STAGE_REQUIRED`); they can still move dist-tags/deprecate versions and retain other permitted write capabilities. Stage-only is not a general read-only/security boundary. [Stage-only tokens](https://docs.npmjs.com/about-access-tokens/#about-stage-only-tokens).
- **Confirmed:** Staged publishing uploads with `npm stage publish`; a maintainer must review/approve with 2FA before it goes live. Staging itself needs no 2FA challenge; account 2FA and publishing rights are prerequisites. It requires an **existing package**, **npm ≥11.15.0**, **Node ≥22.14.0**. [Staging requirements](https://docs.npmjs.com/staged-publishing/).
- **Implication:** Interactive direct publication, stage approval, and a project's maintainer-release approval can be distinct gates. Direct OIDC publication can be unattended when authorized; npm does not infer an extra human release approval from a manually merged GitHub PR. Staged publication is now a native approval mechanism, but choosing it is outside this research.

### 7. npm trusted publishing and provenance

**Claim:** OIDC publishing is package-bound to configured CI identity, requires supported hosted execution/tooling, and is separate from private installation authentication. **Support:** direct evidence, with setup implications labeled. **Confidence:** high except noted operational gaps.

- **Confirmed:** Trusted publishing requires **npm CLI ≥11.5.1** and **Node ≥22.14.0**. Supported providers currently are **GitHub Actions on GitHub-hosted runners**, **GitLab.com shared runners**, and **CircleCI cloud**; self-hosted runners are unsupported. The current docs specify provider/hosting restrictions, not a Linux-only rule; GitHub examples use `ubuntu-latest`. [Requirements/provider list](https://docs.npmjs.com/trusted-publishers/#supported-cicd-providers), [first-party documentation source](https://github.com/npm/documentation/blob/main/content/packages-and-modules/securing-your-code/trusted-publishers.mdx).
- **Confirmed:** Configuration is in an existing package's npm settings; `npm trust` explicitly requires the **package already exists**, package write rights, account 2FA, and **npm ≥11.15.0**, and rejects bypass-2FA tokens for trust management. The exchange API has a package-not-found response. **Implication:** a brand-new downstream package requires authorized bootstrap before adding its trusted publisher; neither staging nor the documented trust setup creates that package for the first time. [Trust prerequisites](https://docs.npmjs.com/cli/v12/commands/npm-trust/#prerequisites), [exchange](https://github.com/npm/api-documentation/blob/main/api/registry.npmjs.com/oidc.yaml), [staging bootstrap restriction](https://docs.npmjs.com/staged-publishing/#prerequisites).
- **Confirmed:** Configure the exact GitHub **organization/user**, **repository**, **workflow filename** (`.yml`/`.yaml`, filename only, present under `.github/workflows/`), and optional **environment name**. All configured fields are case-sensitive exact matches. npm does not validate configuration when saved; mismatches appear at publication. [GitHub identity fields](https://docs.npmjs.com/trusted-publishers/#for-github-actions), [troubleshooting](https://docs.npmjs.com/trusted-publishers/#troubleshooting).
- **Confirmed:** Publishing jobs need **`id-token: write`** to obtain OIDC tokens; the npm CLI detects OIDC and uses it **before falling back to traditional tokens**. No long-lived npm publishing token is needed for the successful OIDC flow. **Implication:** leaving a write token available can obscure a failed OIDC migration; verifying the actual auth path matters. [GitHub permission](https://docs.npmjs.com/trusted-publishers/#github-actions-configuration), [authentication precedence](https://docs.npmjs.com/trusted-publishers/#how-trusted-publishing-works).
- **Confirmed:** Trusted publisher configurations created **after September 3, 2026** automatically allow **`npm stage publish`**; direct **`npm publish`** must additionally be permitted. Older configurations have grandfathered behaviors. The guide currently permits **up to ten** trusted publishers per package; required fields cannot be edited in place—delete/recreate to change them. [Allowed actions/current configuration](https://docs.npmjs.com/trusted-publishers/#step-1-add-a-first-trusted-publisher-on-npmjscom), [management](https://docs.npmjs.com/trusted-publishers/#managing-trusted-publisher-configurations).
- **Confirmed:** With reusable/manual workflow patterns, the troubleshooting guide says matching checks the **calling workflow**, which may differ from the file containing `npm publish`; `id-token: write` must be given to parent and child workflows. **Unverified:** the precise eventual call graph and OIDC claims must be checked before configuring the downstream binding. [Workflow matching caveat](https://docs.npmjs.com/trusted-publishers/#troubleshooting).
- **Confirmed:** Trusted publishing handles publication, **not private dependency installation or arbitrary read authentication**. npm recommends a separate **read-only granular token** for private installs; its example supplies `NODE_AUTH_TOKEN` only to installation, not publication. Public installs do not need a publishing token. [Private dependencies](https://docs.npmjs.com/trusted-publishers/#handling-private-dependencies).
- **Confirmed:** GitHub/GitLab trusted publication automatically generates provenance **without `--provenance`** when the **source repository and npm package are public**. Private-source publication can authenticate through OIDC but has no automatic provenance; CircleCI provenance is currently unsupported. `provenance=false` can explicitly disable it. [Automatic provenance/opt-out](https://docs.npmjs.com/trusted-publishers/#automatic-provenance-generation).
- **Confirmed:** Non-trusted publication can opt into provenance with `--provenance`/configuration on a supported cloud-hosted GitHub/GitLab runner; the provenance guide requires **npm ≥9.5.0**, `id-token: write`, and public repository metadata matching the publishing source. That older provenance minimum does not replace the higher OIDC minimum. [Provenance prerequisites](https://docs.npmjs.com/generating-provenance-statements/#prerequisites), [GitHub configuration](https://docs.npmjs.com/generating-provenance-statements/#publishing-packages-with-provenance-via-github-actions).
- **Confirmed:** For GitHub publication, `package.json.repository.url` must match the **downstream publishing repository**, not an unchanged upstream URL. `provenance-file` takes precedence over automatic OIDC provenance. Provenance links source/build identity; it does **not** certify non-malicious code, correct tests, or upstream byte fidelity. [Repository matching](https://docs.npmjs.com/trusted-publishers/#troubleshooting), [provenance-file precedence](https://docs.npmjs.com/cli/v12/commands/npm-publish/#provenance-file), [provenance limitations](https://docs.npmjs.com/generating-provenance-statements/#provenance-limitations).
- **Implication:** Preserve upstream snapshots independently from downstream registry identity/metadata. Before any later publication, verify runner/tool versions, exact trust binding, allowed action, auth path, public access, repository metadata, and attestation eligibility; this does not select packaging layout or release policy.

## Contradictions

- **Scoped-package default:** General scope/scoped-public guides say private by default; v12 `npm publish` says public for new packages. Both support explicit public access. This report avoids depending on either default. [Scope guide](https://docs.npmjs.com/about-scopes/#scopes-and-package-visibility), [v12 CLI](https://docs.npmjs.com/cli/v12/commands/npm-publish/#access).
- **Trusted-publisher count:** The current trusted-publishing guide permits ten simultaneous publishers, while `npm trust`'s description still says the registry supports one. Do not silently assume CLI parity with the newer multi-publisher setup. [Guide](https://docs.npmjs.com/trusted-publishers/#managing-trusted-publisher-configurations), [CLI description](https://docs.npmjs.com/cli/v12/commands/npm-trust/#description).
- **Granular-token creation:** The generic creation guide still says CLI creation is unavailable; v12 `npm token` documents granular creation/options and the December 2025 completion announcement says it shipped. Use version-specific CLI evidence rather than treating the generic guide as a current prohibition. [Generic guide](https://docs.npmjs.com/creating-and-viewing-access-tokens/#creating-tokens-with-the-cli), [v12 command](https://docs.npmjs.com/cli/v12/commands/npm-token/), [announcement](https://github.blog/changelog/2025-12-09-npm-classic-tokens-revoked-session-based-auth-and-cli-token-management-now-available/).
- **Classic-token dates:** Generic token docs say only granular tokens are supported “as of November 2025”; the November announcement projected November 19, but the completed revocation announcement is December 9. Current prohibition is unambiguous; this report uses the completion date. [Generic docs](https://docs.npmjs.com/about-access-tokens/), [completion](https://github.blog/changelog/2025-12-09-npm-classic-tokens-revoked-session-based-auth-and-cli-token-management-now-available/).
- No conflicting current primary wording was found for the `GITHUB_TOKEN` PR approval exception: both fetched GitHub pages explicitly document it. Older blanket descriptions/search excerpts are not current evidence.
